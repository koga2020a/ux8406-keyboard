==============================================================
 ASUS UX8406MA Fn Lock スクリプト 開発経緯
==============================================================

ChatGPT との対話ログを整形したもの(2026-08-07)。
プロトコル特定に至るまでの試行錯誤の記録として残す。
整形前の時点で、HID の列挙・Feature Report 送信自体は成功して
いたが、Fn Lock が切り替わらない(F1 がミュートのまま)状態
だった。

--------------------------------------------------------------
■ 送信は成功しているのに Fn Lock が変わらない
--------------------------------------------------------------

[ユーザー]
F1 はミュート機能のままでした。

[ChatGPT]
ここまでの結果から、Windows → Bluetooth キーボードへの HID 送信
そのものは成功している。問題は Fn Lock の値または ASUS 側サービス
との連携。

調べ直すと重要な差があった:

- G-Helper は Fn Lock を切り替えるとき、
  「ASUS 本体への ACPI 設定」+「5A D0 4E 00/01 の HID 送信」の
  両方を実行している。HID 部分だけ真似た場合、G-Helper と完全に
  同じ動作ではない。
- Linux の hid-asus では Fn Lock 有効化は明確に「5A D0 4E 01」。
  USB キャプチャの実機報告でも 01 = enable / 00 = disable。

前回は 00 を送ったため、「Fn Lock OFF」を送っただけだった可能性
がある。そこで 01 版を作成
(asus_ux8406_fnlock_on_v3_2_try_01.ahk)。

送信内容:

  初期化:
    5A 41 53 55 53 20 54 65 63 68 2E 49 6E 63 2E 00
    ("5A" + ASCII "ASUS Tech.Inc.")

  Fn Lock ON 候補:
    5A D0 4E 01 00 00 00 00 00 00 00 00 00 00 00 00
             ^^

実行後、F1 が通常の F1 になったか確認してほしい。

なお G-Helper には「UX8406CA で ASUS サービスを止めると Fn キーが
動かず、G-Helper の Fn Lock も効かない。サービスを起動すると動く」
という報告がある。01 でも変化しない場合は、
  Fn+Esc → COL05 の ASUS Vendor HID イベント
        → ASUS Optimization 等のサービス → キーボードへ制御
という経路の仮説が強くなる。その場合は COL05 (InputLen=6) を
Raw Input で監視し、Fn+Esc 押下時の 6 バイトを特定する方向。

--------------------------------------------------------------
■ 成功: 仕組みの確定
--------------------------------------------------------------

[ユーザー]
成功しました!

[ChatGPT]
これで仕組みが実機で確定した。AutoHotkey v2 だけで Windows 標準の
hid.dll を直接呼び、Bluetooth 経由で UX8406MA キーボード本体の
Fn Lock 状態を変更できている。

実機で成立した経路:

  AutoHotkey v2
     ↓ DllCall()
  Windows hid.dll
     ↓ HidD_SetFeature()
  Bluetooth HID
     ↓
  ASUS UX8406MA Keyboard (PID 0x1B2D / COL05)
     ↓
  Fn Lock ON

本命 Collection の情報:

  VID        = 0x0B05
  PID        = 0x1B2D
  UsagePage  = 0xFF31
  Usage      = 0x0076
  FeatureLen = 16
  Report ID  = 0x5A

実機確認結果:

  Fn Lock ON : 5A D0 4E 01 00 ... 00
  Fn Lock OFF: 5A D0 4E 00 00 ... 00

前に試した 00 で変化せず、01 で F1 が通常の F1 になったため明確。

この方法は F1〜F12 を AutoHotkey で個別リマップしているのではなく、
キーボード本体の Fn Lock を変更している。よって F2〜F12 も本来の
機能キーとして動く。

次のステップ: 診断コードを削り、起動時に一度だけ
「5A + "ASUS Tech.Inc."」で初期化し、ホットキーで 5A D0 4E 01/00
をトグル送信する常用スクリプトにする。

--------------------------------------------------------------
■ 常用版: Shift+Ctrl+Esc トグル + ツールチップ
--------------------------------------------------------------

[ユーザー]
Shift+Ctrl+Esc で ON/OFF、ツールチップ表示にしてください。

[ChatGPT]
完成版 (asus_ux8406_fnlock_toggle_shift_ctrl_esc.ahk)。

- Shift+Ctrl+Esc を押すたびに Fn Lock: ON / OFF を交互に切り替え、
  ツールチップを約 1 秒表示。
- 起動時には状態ずれを避けるため Fn Lock をいったん ON に揃える。
- Bluetooth 再接続で HID パスが無効になった場合は再検出する。
- 外部 DLL は不要。Windows 標準の hid.dll 等のみ使用。

--------------------------------------------------------------
■ CapsLock → Ctrl 化
--------------------------------------------------------------

[ユーザー]
CapsLock キーを Ctrl キーとして使えるように(Ctrl+Shift+Esc、
Ctrl+A など)できますか。

[ChatGPT]
追加した。基本は「CapsLock::Ctrl」の 1 行。

  CapsLock + A           → Ctrl + A
  CapsLock + C           → Ctrl + C
  CapsLock + Shift + Esc → Ctrl + Shift + Esc

Fn Lock トグルも CapsLock+Shift+Esc で実行でき、物理 Ctrl も
引き続き使える。この設定では CapsLock 本来の大文字固定は使えなく
なる。

--------------------------------------------------------------
■ ズレ検知の実装(2026-09-02)
--------------------------------------------------------------

- 症状の報告
  たまに Fn Lock の設定がズレる(F キー行がメディアキーに
  戻っている)。Shift+Ctrl+Esc を 2 回押す = 現在の状態を
  もう一度送ると直る。
  → スクリプトが持っている状態 (FnLocked) は正しく、実機側
    だけがズレている、と判断した。

- 読み戻しの実機確認
  (UX8406MA / Windows 11 26200 / ASUS Optimization・
   ScreenXpert 等の ASUS 常駐サービスが多数稼働)
  対象コレクション (COL05) への HidD_GetFeature
  (ReportID 0x5A / 16 バイト) は成功し、最後に
  HidD_SetFeature で書き込んだ 16 バイトをそのまま返した
  (エコー / レジスタ的な挙動)。

    ハンドシェイク送信直後:
      5A 41 53 55 53 20 54 65 63 68 2E 49 6E 63 2E 00
    5A D0 4E 01 送信直後 / 3 秒後 / 13 秒後:
      5A D0 4E 01 00 ... 00   (いずれも同じ値)
    本スクリプト未起動時のベースライン:
      5A D0 3D 64 30 00 ... 00   (意味は未解明)

  所要時間は接続中で 0〜80 ms。
  HidD_GetInputReport (6 バイト) も成功し
  5A 3D 2C 00 00 00 を返した(参考。スクリプトでは未使用)。

- 原因の推定
  BLE 再接続のたびに HID の子ノードは作り直されている
  (DEVPKEY_Device_LastArrivalDate が更新される。親の
   BTHLE\DEV_... は起動時のまま。デバイスパス文字列は同一)。
  つまり DBT_DEVNODES_CHANGED は再接続時に飛んでおり、
  再適用自体は走っているはず。そこで、
    - 再適用の後に ASUS 常駐サービス等が自分の持つ
      Fn Lock 状態を書き戻している
    - 送信は成功扱いでも実機に反映されていない
  といった競合を原因候補とした(確定はしていない)。

- 方針
  読み戻し値は「最後に書かれたレポートのエコー」であって
  Fn Lock の実状態そのものではないが、他ソフトの書き込みや
  デバイスリセットがあれば値が変わるため、ズレの検知には
  使える。そこで 10 秒周期で読み戻して期待値と比較し、
  違っていればハンドシェイク込みで再適用する方式を採用した。
  あわせて Fn Lock 送信の直後にも読み戻しで検証し、
  一致しなければ 1 回だけ再送するようにした。

- 実機テスト
  スクリプト起動中に別プロセスから 5A D0 4E 00(反対値)と
  ハンドシェイク(Fn Lock 以外)を書き込み、いずれも約 8 秒後に
  5A D0 4E 01 へ自動修正されることを確認。接続中に 4 分間
  (10 秒間隔 × 24 回)読み戻しても値は変わらず、ASUS 常駐
  サービスが周期的に書き換えることはなかった。
